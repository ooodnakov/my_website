# Browser OS COM2 control protocol

Status: guest/host v1 wire contract. COM2 is separate from the xterm byte stream on COM1/`ttyS0`; never render COM2 bytes in xterm. The host adapter owns its serial bytes; the guest broker owns raw `/dev/ttyS0`, `/dev/ttyS1`, and the visitor controlling PTY.

## Transport and framing

- v86 enables UART1 (`uart1: true`) and listens to `serial1-output-byte`; UART index 1 is COM2 / guest `/dev/ttyS1`. Host input is `serial_send_bytes(1, Uint8Array)`, never string transport.
- Both COM2 ends use raw, no-echo 115200 8N1. A frame is ASCII `BOS1`, a 16-bit unsigned big-endian payload length, then exactly that many UTF-8 JSON bytes. Payload length is 1–4096 bytes. Read/write APIs may split or combine frames.
- The JSON value is one flat object: no arrays, nested objects, unknown keys, duplicate keys, or non-JSON values. Reject invalid UTF-8, malformed JSON, wrong types, out-of-range values, trailing bytes, and unknown operations. Do not scan/recover to a later marker: send a bounded error when possible, revoke the session, discard COM2 authority, and release held COM1 input in order. The parser retains at most one frame plus its six-byte header.
- Every object has exactly `v:1`, `sessionId`, `seq`, `op`, and the fields in the operation table. `sessionId` is exactly 32 lowercase hex digits generated by the host. `seq` is an integer 1–2147483647, starts at 1 independently in each direction, and increments by exactly one for every frame in that direction. Do not wrap; establish a fresh session before exhaustion. JSON booleans are not integers.
- `fenceId` and `requestId` are strictly increasing, single-use identifiers within a session; an exhausted counter requires a fresh session.
- Maximum object size is eight fields (the `dispatchAction` frame). No shell text, command fragments, URLs, HTML, clipboard payloads, paths, or arbitrary data cross COM2.

## Session and operation schemas

The table lists the complete key set for each operation: session-bound frames have the four envelope keys plus the named operation fields; the first guest `bootstrap` is intentionally sessionless and has only its five listed keys. The guest emits exactly one bootstrap after opening/configuring both raw UARTs and verifying its embedded descriptor. It does not accept host frames until the entire bootstrap frame has been flushed to COM2. The host validates that identity against the pinned manifest and responds with `hello` at host seq 1. The guest adopts that session and emits `ready` as guest seq 1 after applying the validated hello dimensions. The host sends `setLocale` at host seq 2; the guest's matching `localeAck` must be guest seq 2. No advisory or shell-state frames may precede that ACK. `shellReady` is independent and may follow it later.

The guest accepts no host frame until the full bootstrap frame is flushed. |

`action` is exactly one of `tour`, `plugins`, `links`, `projects`, `contact`, `github`, `a`, `ls`, `eza`, or `clear`. The guest maps each enum to a fixed command/function; it never evaluates a string. The `a` action is the existing `eza -lah --git --color-scale all -g --smart-group --icons always --hyperlink auto` alias.

`linkId` is exactly one of: `quick-cv`, `quick-pdf-en`, `quick-pdf-ru`, `quick-archive`, `quick-vcard`, `quick-mail`, `social-discord`, `social-reddit`, `social-x`, `social-twitch`, `social-yt`, `social-ig`, `social-tg`, `social-mastodon`, `social-li`, `social-gh`, `social-tt`, `project-cover-doc`, `project-myspace-exp`, `project-lemma`, `project-articles`, `archive-projects`, `archive-events`, `archive-gallery`, `archive-video`. `copyContact` is valid only with `quick-mail`; all other valid IDs may be used with `open`.

## COM1 fence, editor boundary, and dispatch

The host's `inputBytes` is the cumulative number of raw byte values it has submitted to COM1 with `serial_send_bytes(0, Uint8Array)` in this session; it includes every byte and never wraps. The guest counts raw ttyS0 input bytes, forwards bytes through the fence to the visitor PTY in order, and retains later bytes in a FIFO. COM1 output is never parsed as control data. A new/reset Worker starts a new session and resets both counters; never replay an old frame or fence.

`inputFence` requests consumption proof, not a typed marker. A conforming implementation may report `cleanPrompt` only after the exact cumulative target has crossed the PTY input path and been consumed by ZLE: ZLE must be active, `BUFFER` empty, kernel `PENDING == 0`, ZLE `KEYS_QUEUED_COUNT == 0`, no foreground program owns the PTY, and the key/UTF-8 decoder must have resolved the preceding input at a post-widget safe point. Empty-kernel-queue polling and echoed counters do not prove editor consumption. Zsh's keymap resolver keeps partial escape and UTF-8 state internally; neither these counters nor an injected sentinel attest that state. The current broker tracks bytes written to the PTY only and has no safe decoder-boundary proof.

For a fence whose requested bytes reach the PTY before its deadline, the current broker returns `state: "unknown"`; an incomplete/expired fence revokes the control session with `badValue`. It rejects every `dispatchAction`. Advisory `shellState: "cleanPrompt"` never enables dispatch.

On receipt of `inputFence`, the guest holds all later COM1 bytes in one FIFO, capped at 65536 bytes. The fence plus matching dispatch decision has a strict 1000 ms deadline measured by a monotonic clock. The broker must never overwrite `BUFFER`, edit the line, or inject terminal text. If the fence is not clean, the matching dispatch is stale/malformed, the FIFO reaches its bound, the deadline expires, COM2 is lost, or the protocol is revoked, reject the request and release every held byte unchanged and in original order to the PTY. A full FIFO reports `badValue`, cancels dispatch and revokes the session; it is never silently truncated. `Ctrl+C` remains a native `0x03` tty input/`ISIG` event; if it arrives while bytes are held, cancel the decision and release all preceding held bytes, then the interrupt and any later bytes in their original order without waiting for the fence deadline. Emulator reset remains host-native.

The host may send `dispatchAction` only after a matching `inputFenceAck` reports `cleanPrompt` with the exact same fence and byte count. Any implementation that enables dispatch MUST recheck the one-use fence, empty `BUFFER`, active ZLE, pending/read-ahead counts, foreground process group, session, and request ID immediately before launching the fixed enum. It may ACK `accepted` only after that live check and one-time launch; failed checks reject, consume the fence, and release held input. `accepted` means launched, not completed. Only one fence/dispatch may be outstanding. Any missing ACK by 1000 ms, duplicate/stale ID, reset, or session loss revokes authority; do not retry an ambiguous action. Acquire a fresh fence for each later action. On acceptance or rejection, release buffered bytes unchanged/in order; an action never replaces pending user input. The current guest has no executor satisfying these conditions and rejects every dispatch; no dispatch-ready claim is valid until the proof and live executor exist.

For `portfolioAction`, host `queued` means only that the request entered the host's user-confirmation queue, not that a URL was opened or clipboard data copied. A rejected or unavailable host action returns `rejected`; guest output cannot trigger an automatic user gesture.

## Startup, state, locale, and terminal size

`emulator-ready` means only that v86 initialized. The guest bootstrap proves only that its UARTs are raw/configured and its embedded descriptor has been verified; it carries no session. Host `hello` at seq 1 establishes the session and requests validated initial dimensions. Guest `ready` at seq 1 proves those dimensions were applied to ttyS0 and the controlling PTY. The host then sends its selected initial locale at seq 2; the guest must acknowledge that exact locale at guest seq 2 before emitting any advisory `shellState` or startup `shellReady`. `shellReady` remains a separate startup signal and does not imply an active or clean prompt. Never infer readiness or prompt state from terminal output, text markers, a prompt string, or COM1. `shellState` is advisory and never substitutes for a matching clean `inputFenceAck`.

The root-owned broker starts the visitor as a nonroot login zsh on a controlling PTY; ttyS0 remains raw transport. It validates every dimension before calling `TIOCSWINSZ` for both ttyS0 and the PTY; resizing the PTY produces `SIGWINCH` for the foreground process group. Guest locale selection changes only the root-managed `/portfolio/current` view, never writable home or generated files. The same `setLocale` operation is used by the host and the fixed `set-locale en|ru` wrapper, backed by `guestctl locale`. Before both `ready` and initial `localeAck`, every guest CLI request returns only `error unavailable`; it does not change locale, validate a link/action, or emit a COM2 request.

## Guest build identity

Before `fs.json` is generated, the build emits canonical UTF-8 JSON with a trailing LF at `alpine/guest-build.json`; the byte-identical file is embedded in the rootfs at `/etc/browser-os/guest-build.json`. It deterministically records hashes/versions of every guest build input: pinned base/builder and package inputs, scripts, Dockerfile, source/exporter and canonical EN/RU outputs, guest tools, broker, ZLE hooks, and protocol implementation. `manifest.json` exposes `guest.buildIdentityPath: "alpine/guest-build.json"` and `guest.buildId`, exactly the lowercase SHA-256 of that descriptor asset. The broker hashes its embedded descriptor and reports that digest as `ready.guestBuildId`; the host independently verifies the manifest asset hash and requires equality. This content identity is independent of the `fs.json` byte hash; neither value is reused as the other.

## Revocation and byte-stream isolation

The guest accepts one sessionless `bootstrap`, then exactly one host `hello` per fresh session. Repeated bootstrap/hello, wrong session, any malformed/oversized/stale/out-of-order frame, or operation in the wrong direction sends a bounded `error` where possible, revokes all pending requests/fences, returns held COM1 input in order, and requires a fresh Worker/session. Never resynchronize within an invalid stream. A revoked COM2 channel has no authority to dispatch, resize, or change locale.

COM1 remains the native xterm byte stream: input is raw byte data and output is the tty/PTY byte stream. Preserve terminal echo, editing, UTF-8, foreground programs, `ISIG`, Ctrl+C, and reset. COM2 is never forwarded to COM1, PTY input, a shell command, or terminal output.
